## 1. 项目范围与诚实边界

### 1.1 项目要处理的问题

本项目处理的是以下一组实际问题：

1. Claude Code 需要直接使用本地项目文件，长期依赖远程主机搬运文件不适合日常工作。
2. 目标账号需要与宿主机的日常浏览器、日常网络和个人身份应用分开。
3. 注册、验证、付款和日常使用需要保持同一固定网络出口，减少环境漂移。
4. 网络链任一环节发生故障时，结果需要是来宾虚拟机断网，而不是改走宿主机网络。
5. 配置、虚拟机或中转服务发生损坏后，需要有经过实机演练的恢复路径。
6. 建设过程需要留下可核对的配置版本、测试证据和验收结论。

项目最终形成的不是单一代理配置，而是一套专用虚拟机、固定网络链、失败关闭规则、放行状态、备份恢复材料和运行纪律的组合。

### 1.2 最终采用的设计结论

- **账号与环境一一对应。** 一个目标账号固定在一套专用虚拟机环境中使用。
- **注册时刻作为环境锚点。** 登录身份、验证号码、付款地区、固定出口、时区、语言、键盘布局和 DNS 状态在注册时保持一致；注册完成后，更换出口、恢复旧快照或在本地网络登录均被列为高风险事件。
- **可用性让位于失败关闭。** 隧道、转发、上游认证或放行状态异常时，来宾机保持无外网状态，不自动直连，也不自动切换其他出口。
- **服务运行不等于正式放行。** VPS 上的服务可以处于运行状态，但只有事实、规则和配置完成核对并生成放行记录后，链路才进入已放行状态。
- **备份不等于旧快照回滚。** 备份用于恢复配置和重建链路；注册完成后，整机恢复到注册前快照不属于日常恢复手段。
- **秘密不进入成果材料。** 本公开稿只保留架构、类别、状态和结论，不保留能够接管环境或账号的值。

### 1.3 诚实边界

#### 1.3.1 不保证不封号、不保证账号一定可用

本方案只能降低环境不一致、网络漂移和误操作带来的风险，不能控制平台的全部判断。平台可能综合考虑账号历史、登录行为、支付信息、设备与浏览器特征、网络声誉、使用模式等多种信号。任何声称“用了某套代理或虚拟机就一定不封号”的说法都不可靠。

如果某个身份、账号或支付工具本身已经受限，这套环境不能把该事实洗掉，也不应被理解为绕过既有处罚的方法。

#### 1.3.2 物理位置不会因网络出口而改变

虚拟机流量可以从目标地区出口离开，但使用者的物理位置、宿主机所在地、设备本身的某些区域属性并不会因此改变。网络出口解决的是流量路径和对外呈现地址，不等于把整个人和整台设备搬到了目标地区。

是否符合目标服务的地区资格，应按服务条款和真实情况判断，不能把技术链路当作资格证明。

#### 1.3.3 虚拟化痕迹无法靠本方案消除

来宾系统运行在虚拟化平台上。来宾内程序可能通过 CPU、固件、显卡、计时、设备枚举、虚拟化检测接口等方式判断自己位于虚拟机中。本方案不做硬件伪装，也不承诺“看起来和实体机完全一样”。

本项目接受的边界是：

- 不伪造宿主机硬件身份；
- 不追求绕过虚拟机检测；
- 只保证网络、工作文件和账号使用环境受控；
- 如果目标场景明确不接受虚拟化环境，本项目不以继续堆叠伪装手段处理。

#### 1.3.4 住宅出口也有历史和声誉问题

“住宅”“静态”“独享”只是采购类别，不等于这个地址从未被别人使用过。需要特别接受以下已知弱点：

- 地址可能来自租用号段；
- 号段可能没有 PTR 记录；
- 注册信息、地理数据库和运营商自报位置可能不完全一致；
- 地址可能曾被前任使用者用于其他用途；
- 数据库中的国家、城市、ASN、欺诈分会随时间变化；
- 供应商所说的“独享”难以由购买者独立证明其全部历史。

因此，出口体检只能发现当前可见风险，不能证明地址“绝对干净”。

#### 1.3.5 链路中可能存在明文代理段

典型链路中，来宾机到 VPS 的 WireGuard 段是加密隧道，浏览器到目标站点的 HTTPS 也是端到端加密；但 VPS 到上游住宅出口若使用普通 SOCKS 协议，该段的代理认证信息可能不是加密传输。本项目对这一段的结论是：不能笼统称为“全程加密”，供应商协议和认证方式属于已记录的风险项。

#### 1.3.6 浏览器与系统指纹仍会说话

即使出口地址正确，下列不一致也可能暴露环境问题：

- 时区与出口地区不一致；
- 系统语言、浏览器语言和付款地区互相冲突；
- 英国键盘布局未生效，导致密码中的符号输入错误；
- WebRTC 或本地网络发现暴露宿主机地址；
- 字体集明显来自另一类系统；
- 宿主机代理变量被虚拟机平台注入到来宾会话；
- 同一虚拟机中登录了带真实身份的聊天、邮箱或社交应用。

本方案通过基线检查降低这些问题，但不承诺浏览器指纹与普通当地用户完全一致。

## 2. 总体架构与最终形态

### 2.1 逻辑拓扑

```text
使用者
  │
  ├─ 宿主机桌面启动器 ──> 远程桌面 ──> 来宾虚拟机桌面
  │                                      │
  │                                      ├─ Claude 浏览器版 / 桌面端
  │                                      ├─ Claude Code
  │                                      ├─ 本地项目目录
  │                                      └─ 固定同步目录 <同步目录>
  │                                             ⇅ 双向同步
  └─ 宿主机固定同步目录 ────────────────────────┘

来宾虚拟机
  │  WireGuard 加密隧道
  ▼
境外 VPS <VPS_IP>
  │  受控转发服务 + 放行闸门
  │  经认证的上游代理连接
  ▼
目标地区静态住宅 / ISP 出口 <出口_IP>
  │
  ▼
目标服务
```

手机作为第二个独立 WireGuard 对端接入同一条链，出口仍为同一个 `<出口_IP>`。手机对端与来宾机对端分别登记、分别握手，手机接入和断开不改变来宾机配置。

### 2.2 宿主机与来宾机

宿主机承担虚拟化平台、虚拟机镜像、远程桌面入口、固定同步目录和备份存储。宿主机日常网络不承载目标账号流量。

来宾机是目标账号的日常工作环境，最终运行状态包括：

- 浏览器、Claude 桌面端和 Claude Code 已安装；
- 全部普通外网流量进入 WireGuard 隧道；
- 物理网卡不承担普通外网默认流量；
- 全球 IPv6 地址为零，IPv6 不形成旁路；
- 时区、系统语言、地区格式和键盘布局与目标地区一致；
- 宿主机代理变量在来宾机的命令行会话、图形会话和用户服务环境中均已清除；
- 与目标工作无关的真实身份应用不进入该环境；
- 虚拟机配置在建设后期由 4 个虚拟 CPU、8 GiB 内存调整为 6 个虚拟 CPU、16 GiB 内存。宿主机资源足以承载该配置；该调整只影响计算资源，不改变网络出口和链路延迟。

### 2.3 文件同步通道

宿主机与来宾机之间最终只保留一个固定同步目录，位置在外置存储上，来宾机一侧对应固定的家目录子目录。同步状态在验收时达到以下结果：

- 宿主机新建的文件能够出现在来宾机；
- 来宾机新建的文件能够出现在宿主机；
- 一侧删除文件后，另一侧同步删除；
- 同步服务在虚拟机重启后恢复监视状态；
- 同步目录之外不开放整个宿主机家目录。

该目录的定位是文件传送通道，不是唯一备份位置。删除同步已经实测成立，因此重要文件在该目录之外另有备份。

### 2.4 WireGuard 与 VPS 转发

来宾机与 VPS 之间使用 WireGuard。来宾机和手机分别使用独立对端，来宾机对端承担日常流量，手机对端只在预定场景下接入。

VPS 同时承担以下功能：

1. 终止 WireGuard 隧道；
2. 识别已登记的对端；
3. 运行受控转发服务；
4. 通过经认证的上游代理连接目标地区出口；
5. 保存每次放行对应的事实和版本状态。

VPS 上的事实与放行状态保存在运行时目录中，随 VPS 重启消失。服务进程在 VPS 重启后即使自动恢复运行，也不会自动恢复为已放行状态；放行需要重新生成事实并完成核对。

最终放行记录与配置哈希、SOCKS 端点、对端数量、事实版本和守卫规则摘要绑定。转发配置的关键文件保留哈希，防火墙规则保留可比较的形态摘要。转发链中不存在意外的 NAT 旁路。

### 2.5 DNS、IPv6 与失败关闭

最终网络状态包含以下结果：

- 来宾机使用受控 DNS，浏览器体检时未发现宿主机网络地址经 WebRTC 暴露；
- 来宾机全球 IPv6 地址数量为零；
- 来宾机防火墙存在默认拒绝策略；
- WireGuard 握手持续更新，来宾机实际出口为登记的 `<出口_IP>`；
- 上游代理认证被人为改错后，来宾机断网，抓包中没有允许清单之外的外网流量；
- VPS 未放行、转发服务异常或隧道异常时，链路保持失败关闭，没有自动改走宿主机网络。

### 3.1 网络线的最终结论

网络建设的各个阶段均已关闭。最终链路同时满足以下状态：

- 来宾机默认不直接使用宿主机网络出站；
- 隧道和 VPS 转发是普通外网流量的唯一路径；
- 上游认证失败时没有旁路流量；
- VPS 重启后不会自动保留旧放行状态；
- 来宾机重启后，时区、代理变量、转发规则和远程桌面能够恢复到基线；
- 手机作为独立对端接入时，不改变来宾机的网络身份；
- 备份恢复完成后，链路能够重新放行并通过端到端检查。

### 3.2 浏览器基线结论

来宾浏览器在最终检查中呈现以下结果：

- 显示出口与登记出口一致；
- DNS 使用受控解析；
- 时区和系统语言处于冻结基线；
- 面向站点的语言设置为目标地区语言；
- WebRTC 检查未发现宿主机地址可供暴露；
- 字体集为来宾系统原生集合，该项作为已接受的环境特征保留。

## 4. 评审与核验形成的结论

项目实施中设置了牵头、唯一执行和独立只读评审三个角色，并以异步信件和工单作为工作载体。以下只发布已经形成的评审结论、被确认的问题和最终验收结果，不再展开协作过程。

### 4.1 设计定案

#### 4.1.1 链路形态定案

最终链路定为“来宾虚拟机 → WireGuard → VPS 受控转发 → 目标地区固定出口”。宿主机网络、手机本地网络和临时代理不作为目标账号的日常出口。

#### 4.1.2 失败关闭定案

隧道、VPS 转发、上游认证、DNS 或放行状态任一异常时，来宾机的预期状态均为断网。最终实现中没有隧道失败自动直连、代理失败自动换线或未放行自动放行。

#### 4.1.3 放行状态定案

VPS 的服务状态和放行状态是两个不同概念：

- 服务运行只说明进程存在；
- 放行状态由当次事实、配置哈希、规则形态和核对结果共同生成；
- 放行状态保存在运行时目录，VPS 重启后消失；
- VPS 重启后必须重新生成事实和放行记录；
- 旧放行编号不能跨 VPS 引导周期直接沿用。

#### 4.1.4 对端隔离定案

来宾机和手机使用独立 WireGuard 对端。手机对端的增加改变了 VPS 侧的规则和路由记录，但没有改变来宾机对端、目标出口或来宾机的实际网络地址。

#### 4.1.5 备份与快照定案

配置备份、虚拟机镜像副本和云端旧快照不是同一概念。项目最终保留的是经过哈希校验的备份包和镜像副本；注册完成后，不把恢复到注册前整机快照作为故障处理方案。

#### 4.1.6 自动更新定案

来宾机自动更新最终被保留。保留的前提不是假设更新无风险，而是自动更新曾经真实触发过网络规则丢失，修复后的持久化机制已经通过网络服务重启和整机重启验证。

### 4.2 评审确认并修正的关键问题

| 问题 | 评审与实测发现 | 最终处理结果 | 结论 |
|---|---|---|---|
| 离线测试通过但实机执行失败 | 离线测试未覆盖实机驱动路径；后续实机尝试又陆续暴露出封存执行路径遗漏、真实数据格式未覆盖、投影数据过期和证据绑定不完整等问题 | 重新修订执行合同，统一设计文本、投影、封存载荷和实机证据之间的绑定关系，并重新进行同形态预演 | 离线全通过不能单独构成实机放行依据；最终实机尝试通过，前述缺口关闭 |
| 真实 TCP 流量异常 | 初期转发网络栈在合成检查下不能充分反映真实 TCP 工作负载 | 调整转发网络栈模式后重新完成端到端验证 | 最终网络栈通过真实 TCP 场景验收 |
| 上游认证失败时的旁路风险 | 需要证明认证失败不是只显示错误，而是确实不产生其他出站路径 | 人为改错认证信息后，来宾机断网，抓包结果只包含允许清单内流量 | 认证失败场景达到失败关闭标准 |
| “服务已启动”造成假放行 | 转发服务进程运行并不代表事实和规则已经生成 | 把事实与放行状态改为运行时生成，并与配置、规则和核对结果绑定 | 服务启动本身不能形成放行状态 |
| 关闭链路后的残留状态 | 链路关闭后仍有少量返回规则、路由和交集放行项存在 | 对照设计逐项确认残留来源和用途，并以实际流量与抓包作为判断依据 | 这些残留属于设计内状态，不构成旁路 |
| 宿主机代理变量的初始判断错误 |  最初怀疑的虚拟化代理传播开关本身已经关闭，继续追查后确认，真正来源是来宾机每次启动时由配置数据重写的系统环境文件 | 对启动时重写的环境文件做持续清理，并增加用户服务环境重置；多次全新登录后分别检查命令行、图形和用户服务表面 | 代理变量的根因不是单个开关，而是启动配置的重复生成；最终三类表面检查均为零 |
| 自动更新破坏转发持久化 | 系统更新触发网络服务重启后，隧道所需的外部策略规则被清除，来宾机断网但没有泄漏 | 为网络服务增加不清理外部路由策略的持久化设置，并重新注入规则 | 修复结果通过网络服务重启和整机重启两项验证，自动更新得以保留 |
| 出口是否需要在最后阶段更换 | 复检结果与早期基线逐项一致，国家与城市未漂移，欺诈与黑名单状态未变化，已知号段弱点未恶化 | 最终保留已完成基线和复检的出口，不在环境冻结前临时更换 | 出口选择以连续两次一致的检查结果定案 |
| 手机对端扩展是否影响原链路 | 新增手机对端需要同步调整 VPS 的防护规则和路由记录，存在误伤来宾机对端的可能 | 独立生成手机对端，重新放行后分别检查来宾机出口、手机出口和服务端握手 | 两个对端出口一致，来宾机链路未受影响 |
| 备份能否真正恢复 | 只有文件存在不能证明恢复路径可用 | 从备份实际装回配置，完成逐项比对、重新放行和端到端检查 | 备份恢复路径成立，演练结果形成新的放行引用 |
| VPS 重启时长时间停顿 | VPS 在一次重启验证中于内核启动前停留数分钟，需要人工在云控制台继续启动 | 该现象被单独记录为可用性问题；等待期间链路离线但保持失败关闭 | 该问题不构成网络泄漏，列为已知的非安全残留项 |

### 4.3 最终验收结论

评审与实测最终形成以下结论：

1. **网络阶段全部关闭。** 基础搭建、实机验证、正式放行、补充阶段、重启验证和认证失败注入均已完成。
2. **失败关闭成立。** 上游认证失败和自动更新引发的断网事件中，均未发现允许清单之外的外网流量。
3. **放行机制成立。** 放行状态与当次事实、配置哈希、规则形态和 VPS 引导周期绑定，服务自启不会冒充已放行。
4. **持久化问题关闭。** 来宾机转发规则、目标时区和代理变量清理均已通过重启后的复查。
5. **双对端形态成立。** 来宾机和手机使用独立身份接入同一出口，服务端握手和实际出口均已核对。
6. **备份恢复成立。** 备份包哈希复核通过，配置装回、重新放行和端到端验证已经实际完成。
7. **出口结论稳定。** 基线与冻结前复检结果一致；无 PTR、租用号段和代理段明文认证等弱点继续作为已知风险保留。
8. **非安全残留已被定性。** VPS 重启时可能需要在云控制台人工继续启动，该问题只影响恢复时间，不改变失败关闭结论。

## 7. 踩坑录

### 7.1 宿主机代理被带入来宾机

**现象：** 来宾机在命令行、图形会话或用户服务环境中出现宿主机代理变量。单次删除后，虚拟机重启，变量重新出现。

**根因：** 虚拟化平台在来宾机启动时通过配置数据重写系统环境文件；用户服务管理器随后又把这组变量带入服务环境。最初怀疑的代理传播开关并不是实际来源。

**修法：** 对系统环境文件做开机持续清理，并增加用户服务环境重置。修复后在多次全新登录中分别检查三类表面，代理变量均为零。启动后极短时间内仍可能存在清理窗口，因此验收时间点放在机制执行之后。

### 7.2 宿主机反复重置来宾机时区

**现象：** 来宾机时区已经设置为目标地区时区，但虚拟机重启后又回到宿主机时区。一次性修改系统时区无法保持。

**根因：** 虚拟化平台在启动来宾机时按宿主机环境重新施加时区设置，覆盖了来宾机内部已经保存的值。

**修法：** 在来宾机内设置定时断言：开机后短时间内把时区拉回目标地区，并周期性重复检查。最终结果是，整机重启后时区能够自动恢复，后续复查保持目标时区。

### 7.3 自动更新清掉 WireGuard 策略规则

**现象：** 来宾机自动升级系统组件后，网络服务随之重启，WireGuard 依赖的两条外部策略规则被清除，来宾机突然断网。

**根因：** 网络服务默认会清理不属于自身管理的外部路由策略规则，而隧道工具写入的规则正属于这一类。

**修法：** 为网络服务增加“不管理外部路由策略规则”的持久化设置，并恢复被清除的规则。修复后分别进行网络服务重启和整机重启测试，两次均未再丢失规则。事件期间链路保持失败关闭，没有流量旁路。

### 7.4 VNC 启动守护把自己误判为 VNC 已运行

**现象：** 来宾机重启后，远程桌面端口没有服务，但启动脚本却跳过启动步骤。桌面无法连接的问题反复出现。

**根因：** 启动脚本用包含进程名的模糊匹配检查 VNC 是否运行，脚本自己的命令行里也包含同一字符串，结果把自身误判为 VNC 进程。

**修法：** 把检查改为精确进程名匹配，并最终把远程桌面改为开机启动的系统服务，同时在服务启动前清理失效锁文件。修复后从来宾机监听和宿主机连接两侧均完成验证。

### 7.5 桌面会话和后台进程不在同一条 D-Bus 总线上

**现象：** 桌面面板已经显示拼音输入法，但从后台服务方式启动的浏览器和桌面应用中，输入仍直接产生英文字母。密钥环服务在这些应用中也表现为不可用或状态不一致。

**根因：** 远程桌面会话使用一条独立的会话总线，而由用户服务管理器启动的应用连接的是另一条用户总线。输入法和密钥环注册在桌面会话总线上，后台启动的应用找不到它们。只给应用补输入法环境变量仍不够，因为应用连接的总线地址不对。

**修法：** 让浏览器和桌面应用在桌面会话的总线环境中启动，同时带齐输入法模块和会话地址。修复后，输入法服务和密钥环服务都能在同一条桌面会话总线上被核对到。

### 7.6 没有 PAM 登录时，GNOME Keyring 不自动解锁

**现象：** 桌面应用提示没有可用的系统密钥环，或要求解锁登录密钥环。密钥环程序已经安装，但服务没有以已解锁状态进入桌面会话。

**根因：** 远程桌面会话不是经显示管理器和 PAM 正常登录建立的，原本由登录过程完成的密钥环启动与解锁没有发生。后来增加的普通自启项在一次虚拟机重启后也没有可靠执行。

**修法：** 在这台单一用途来宾机中，登录密钥环采用空密码方式，并把守护进程的启动与解锁放入桌面会话启动环境。验收点改为：桌面会话总线上能够看到密钥环的秘密服务已被实际进程持有，而不是只检查软件包存在。

### 7.7 桌面锁屏不适合远程桌面专用机

**现象：** 来宾桌面出现锁屏界面，远程连接时无法像坐在实体机前一样自然处理。

**根因：** 桌面屏保、电源管理和另一套桌面锁屏设置同时存在于来宾系统中，空闲后会独立触发锁定。

**修法：** 关闭来宾机内部的屏保锁定、电源管理锁屏和桌面会话锁屏，并保留宿主机与远程访问层面的访问控制。该处理只针对单一用途的远程桌面虚拟机，不把来宾机锁屏作为账号安全的主要边界。

### 7.8 VPS 重启在内核启动前停顿

**现象：** VPS 重启后长时间没有进入系统，需要在云服务商控制台人工按键后才继续启动，整条网络链在此期间离线。

**根因：** 停顿发生在内核启动前，与 VPS 内部服务无关，指向云平台虚拟控制台、引导终端或超时策略之间的交互。该问题没有在不扩大变更范围的前提下强行修改引导配置。

**修法：** 把 VPS 重启列为需要人工在场的维护动作，重启后重新执行事实生成和放行，并检查引导周期是否变化。等待期间链路保持离线和失败关闭，因此该问题被定性为可用性残留，而不是安全问题。

### 7.9 目标地区键盘布局导致符号输入错误

**现象：** 在密码等敏感输入场景中，个别符号与使用者按宿主机键盘习惯输入的结果不同，容易被误判为密码错误。

**根因：** 来宾机使用目标地区键盘布局，部分符号键位与宿主机常用布局不同。

**修法：** 将键盘布局作为环境基线的一部分固定下来，并在非敏感字段中实际输入常用符号确认键位。敏感字段输入前先确认当前布局，不用连续试错消耗登录机会。

### 7.10 目标应用自身的软件包架构不匹配

**现象：** 目标桌面应用自动下载的软件包与来宾机处理器架构不一致，直接安装不可用。

**根因：** 来宾机使用 ARM 架构，自动下载入口给出的默认包面向另一种架构。

**修法：** 改从官方软件源安装与来宾机架构对应的版本，并在安装前核对官方签名密钥指纹。最终桌面应用和命令行工具均以与来宾机一致的架构安装。

## 8. 日常运行与维护状态

### 8.1 账号使用状态

目标账号完成注册后，只在专用虚拟机环境中使用，并持续使用同一登记出口。宿主机日常浏览器、其他本地网络和无关设备不登录该账号。来宾机中不混入与目标工作无关的真实身份应用。

### 8.2 固定出口状态

固定出口在注册前完成基线检查，在环境冻结前完成复检，两次结果一致。注册完成后，更换出口被列为高风险变更，不作为普通故障处理手段。

出口订阅的自动续订处于关闭状态，项目为到期前设置了三档提醒，分别位于到期前约两个月、约一个月和最后一周。续订与否由所有者在提醒到达时决定，避免在无人确认的情况下自动改变订阅状态，也避免到期后出口被回收才发现。

### 8.3 电话号码保活状态

用于环境锚定的电话号码只保留给本项目使用，不用于无关服务的批量注册。号码的 PUK 等恢复材料已经归档到受控位置。

号码保活采用付费外发动作作为有效活动，维护周期短于运营商的号码回收期限，并预留了提前量。下一次保活窗口已经进入项目维护记录；到期前若没有完成保活，该事项会被重新提出，而不是默认视为已经处理。

### 8.4 自动更新状态

来宾机自动更新保持开启。自动更新曾经触发的网络规则丢失、时区重置和代理变量重入问题，均已分别形成持久化处理：

- 网络服务不再清除隧道所需的外部策略规则；
- 时区由开机后的定时断言拉回目标地区；
- 代理变量由启动清理和用户服务环境重置持续中和；
- 远程桌面由系统服务在开机时启动。

在一次包含资源调整的整机重启后，复查结果为：来宾机实际出口未变、WireGuard 握手正常、默认拒绝策略存在、全球 IPv6 地址为零、代理变量为零、时区仍为目标地区、VPS 引导周期和放行状态未变化、文件同步仍处于监视状态。

### 8.5 文件交换状态

宿主机与虚拟机之间只使用一个固定同步目录交换文件。该目录已经通过双向新建和删除传播测试，虚拟机重启后同步服务仍能恢复监视。

同步目录不承担唯一备份职责。密码、验证码、私钥、支付材料和其他账号恢复信息不长期保存在同步目录中。

### 8.6 变更处理状态

项目最终把以下事项列为所有者决策事项：

- 更换固定出口、VPS、登录身份或付款地区；
- 在本地网络或新设备上登录目标账号；
- 恢复注册前整机快照；
- 弱化或关闭失败关闭规则；
- 删除虚拟机镜像、备份或账号恢复材料；
- 新增付费、续费或重新采购。

明确的程序修复、已定案范围内的配置恢复和可用性修复，不改变上述边界。每次涉及网络安全姿态的变更，都重新生成事实、更新放行记录并做独立复查。

### 8.7 当前已知残留

截至 v1 发布，项目保留以下已知事项：

1. 住宅出口无 PTR、号段属于租用范围，该属性没有因体检通过而消失。
2. VPS 到上游代理的一段使用普通 SOCKS 协议时，代理认证不具备独立的传输层加密。
3. VPS 重启时可能停留在内核启动前，需要人工在云控制台继续。
4. 虚拟机硬件特征仍可被来宾内程序识别，本方案没有进行硬件伪装。
5. 跨国链路延迟和远程桌面软件渲染带来的不流畅感仍然存在；增加虚拟 CPU 和内存只能改善计算任务，不能消除这两项限制。

以上事项均已定性，不影响“网络链已建成、失败关闭已验证、备份恢复已演练”的项目结论。
